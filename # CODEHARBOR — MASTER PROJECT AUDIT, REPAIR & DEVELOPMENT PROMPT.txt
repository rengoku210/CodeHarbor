# CODEHARBOR — MASTER PROJECT AUDIT, REPAIR & DEVELOPMENT PROMPT

You are the lead software architect, senior full-stack engineer, and autonomous development agent responsible for completing CodeHarbor, an existing browser-based IDE project.

Your mission is to inspect the entire existing project, understand its original vision, identify problems, repair broken functionality, and implement its intended features until it becomes a genuinely usable browser-based development environment.

This is an existing project. Do not casually throw away previous work or rebuild everything from scratch.

## 1. First Understand the existing project

Before changing anything

1. Inspect the complete project directory and its structure.
2. Read all README files, documentation, configuration files, package manifests, and relevant source files.
3. Inspect existing UI components, backend services, APIs, routes, database schemas, and authentication logic.
4. Inspect existing screenshots, design references, and assets if present.
5. Identify which features are implemented, partially implemented, broken, mocked, or completely missing.
6. Identify the current framework, programming languages, dependencies, and deployment architecture.
7. Run the existing application and inspect its actual behavior.

Do not assume the existing implementation is correct just because it looks finished.

Create an internal feature audit before implementation. Briefly report the most important findings, then proceed with the work without waiting for permission.

## 2. Product vision

CodeHarbor is intended to be a browser-based coding environment inspired by the usability and workflow of Visual Studio Code.

It should allow developers to

- Create and manage projects.
- Open and edit files directly in the browser.
- Navigate folders and project structures.
- Use an integrated terminal.
- Run and test applications.
- Preview websites and applications.
- Manage source control.
- Install and use coding extensions.
- Customize their development environment.

The final product should feel like a real development tool, not a static demonstration or a collection of UI mockups.

Preserve the existing CodeHarbor identity and design direction. Maintain a polished, professional interface with a familiar IDE layout.

## 3. Critical priority Real editor and extension support

This is the most important technical requirement.

I do not want an editor that merely looks like VS Code.

Investigate how to integrate a real browser-accessible development environment with genuine extension-host functionality.

Investigate suitable existing technologies, including

- code-server
- OpenVSCode Server
- Monaco Editor where appropriate
- VS Code-compatible extension ecosystems
- Other technically suitable open-source components

Compare the options against the existing project architecture before choosing an implementation.

### Extension requirements

The Extensions section should eventually support

1. Searching available extensions.
2. Viewing extension descriptions, publishers, versions, and compatibility.
3. Installing extensions.
4. Enabling and disabling installed extensions.
5. Uninstalling extensions.
6. Managing installed extensions.
7. Persisting extension installations between sessions.
8. Displaying installation errors and compatibility problems.

Most importantly, extensions must actually load and work inside the development environment.

Do not build a fake extension marketplace where clicking Install only changes a visual label.

Do not claim full VS Code extension compatibility unless it has been tested.

If full extension support requires a different editor runtime or workspace architecture, implement the necessary integration rather than hiding the limitation.

If the complete extension ecosystem cannot reasonably be implemented immediately, establish a working foundation with real extension installation and loading, document compatibility limitations, and create a clear roadmap.

## 4. Core IDE functionality

Audit and implement the following features based on the existing architecture.

### A. Workspace and Explorer

- Create, open, rename, and delete projects.
- Display a real folder and file tree.
- Create, rename, move, and delete files and folders.
- Open files in editor tabs.
- Refresh the Explorer.
- Preserve workspace state.
- Handle file operations safely.

### B. Code editor

- Real syntax highlighting.
- Multiple editor tabs.
- File saving and dirty-state indicators.
- Search within files.
- Go to line.
- Basic formatting support.
- Keyboard shortcuts.
- Editor settings.
- Theme support.
- Useful error and diagnostic presentation.

### C. Integrated terminal

- A functional terminal connected to the actual workspace environment.
- Execute real commands.
- Maintain command output and session state.
- Support multiple terminal sessions where feasible.
- Handle errors and process termination.

Do not simulate terminal output.

### D. Run and preview

- Run projects using their actual runtime.
- Support common web development workflows.
- Provide a browser preview for running web applications.
- Display runtime errors and build failures.
- Allow stopping and restarting processes.

### E. Source control

- Git status.
- Changed-file indicators.
- Diff viewing.
- Commit creation.
- Branch information.
- GitHub integration where supported.

### F. Extensions

Treat extension functionality as a core product feature rather than a decorative sidebar.

### G. Settings and developer experience

- Settings interface.
- Keyboard shortcuts.
- Command palette.
- Theme selection.
- Workspace preferences.
- Status bar information.
- Useful loading and error states.

## 5. Backend architecture and security

Inspect whether the current backend architecture can reliably support multiple workspaces and users.

Pay special attention to

- Workspace isolation.
- Authentication and authorization.
- Persistent file storage.
- Terminal process management.
- Runtime isolation.
- WebSocket connections.
- API security.
- File path validation.
- Resource consumption.
- Process cleanup.
- Secrets and environment variables.

Never expose unrestricted server shell access to unauthenticated users.

Prevent path traversal, accidental cross-user file access, and insecure command execution.

Do not put private server credentials in frontend code.

If the current architecture cannot safely support a required feature, improve the architecture before implementing it.

## 6. Development strategy

Work incrementally. Do not attempt a giant rewrite.

Follow this order

Phase 1 — Audit and repair
- Identify existing bugs.
- Fix broken imports, dependencies, APIs, and components.
- Repair the existing application startup process.
- Remove dead or misleading functionality.

Phase 2 — Real development environment
- Establish the actual editor runtime.
- Connect workspace file access.
- Implement persistent workspaces.
- Establish the terminal integration.

Phase 3 — Extension ecosystem
- Implement the real extension installation workflow.
- Connect extension management to the editor runtime.
- Test installing, loading, and using a compatible extension.

Phase 4 — IDE functionality
- Implement Explorer, tabs, search, source control, settings, and command palette.
- Connect all controls to actual functionality.

Phase 5 — Execution and preview
- Implement project execution.
- Connect preview functionality.
- Improve error reporting and developer workflow.

Phase 6 — Quality and polish
- Fix visual inconsistencies.
- Improve responsiveness.
- Add loading, empty, and error states.
- Test complete user workflows.

Prioritize working end-to-end functionality over implementing dozens of incomplete features.
